# ADR-0045: 素材はネイティブ解像度で保存し、拡大は書き出しの直前にやる

Status: Accepted
Date: 2026-10-09
Decider: Claude（Architect）。制作者の問い（2026-10-09「vpipe-api はわざわざ引き伸ばして
ファイル容量が増えたものを送って来てるんですね。実際に作ったサイズのものを送ってもらって
容量減らしつつ、画面にも正規解像度が表示され、実際に動画を再生する時に初めて引き伸ばせば
いいのかなと思ったけど、そうなってない理由が何かある？」）

## できあがり

Take の素材が、H3 が実際に描いた大きさのまま保管庫に入る。Take 比較の「大きさ」は
その本当の値を出す。拡大は書き出しの直前に 1 回だけ、ffmpeg の Lanczos でやる。

| | いま | これ |
|---|---|---|
| 保管庫の中身 | 1920×1080（引き伸ばし済み） | **1344×756**（H3 が描いた大きさ） |
| 画面の「大きさ」 | 1920×1080（嘘ではないが実態と違う） | **1344×756**（実態） |
| 容量 | 436 件 1853 MB | **約 40% 減** |
| 拡大する場所 | vpipe-api（生成のたび） | **書き出しの直前（1 回）** |
| 符号化の回数 | 2 回（vpipe で拡大後 → 書き出し） | **2 回**（中間 → 書き出し。拡大は 1 回だけ） |

## Context

Take 比較に大きさと容量を出したところ、制作者が「1920×1080 なのに 7.5MB なのが気になる。
実際の mp4 の解像度が知りたかった」と言った。

調べると、画面の数字は実ファイルどおりだった（Take の素材 436 件すべてで DB と ffprobe が一致）。
ただし**中身は 1080p ではない**。H3 が実際に描くのは段と比で決まる大きさ（16:9 なら
draft 832×480 / standard 1024×576 / final 1344×768）で、1920×1080 は vpipe-api が
Lanczos で引き伸ばした結果である。

引き伸ばしを頼んでいるのは ixa 側だった（`buildVpipeBody` が Project の解像度を `output` に入れる）。
その理由は ADR-0031 §3 に残っている——「technical レビューの解像度の検査も通る」。
`packages/review/src/technical.ts` の `checkResolution` は Project の解像度より小さい Take を
**fail** にし、ADR-0005 により technical が fail すると LLM のレビュー層が走らない。

**検査を直す代わりに、入力のほうを変えていた。** 書き出しのときに拡大しても画質は同じなので、
この検査は本来は問題でないものを落としている。

## Decision

### 1. vpipe-api に `native: true` を足してもらう（切り抜きまでは向こうがやる）

`output` は必須のまま残す（どの生成サイズを使うか・狙いの画角を決めるのに要る）。
`native: true`（既定 false）のとき、サーバは**生成サイズを `output` の比率に中央で切り抜くだけ**で
拡大しない。1920×1080 を頼んだときの中身はこうなる。

| 段 | 生成サイズ（切り抜く前） | 返るファイル（切り抜き後） |
|---|---|---|
| draft | 832×480 | **832×468** |
| standard | 1024×576 | **1024×576**（すでに 16:9。切り抜き無し） |
| final | 1344×768 | **1344×756** |

**切り抜きをこちらで再現しない。** 生成サイズは 7:4 などで 16:9 ではないため、
cover の規則（拡大後の丸め・切り抜きの基準点・4:2:0 に合わせた偶数への切り下げ）を写すと必ずズレる。
サーバが比率まで合わせて返せば、ixa に残る仕事は**縦横同じ倍率の拡大だけ**になる
（1344×756 → 1920×1080 はちょうど 1.428571 倍）。**規則を書き写すなら差し替え口を作る**（L-016 と同じ形）。

いまのサーバ出力との画角の差は生成サイズで 1 画素未満（いまは上 5.6 行・下 6.3 行、native は上下 6 行ずつ）。

**切り抜きは正確に中央。** 偶数への寄せで片側へ偏ることは無い。生成サイズも切り抜き後の寸法も
偶数なので落とす量の合計は必ず偶数になり、かつ切り抜きは 4:2:0 に変換する**前**（4:4:4 の中間）で
行うため、片側が奇数でもそのまま切れる。vpipe-api 側が可逆の中間ファイルで検算済み
（正解と PSNR 51.9 dB、1 行ずらすと約 30 dB）。

**この規則は `native: true` のときのもので、いまの cover + 拡大の経路とは別。**
2 つの経路で丸め方が違うこと自体が、こちらで写してはいけない理由になっている。

### 2. 本当の大きさはサーバの申告を使う（表を書き写さない）

段と比の対応表を ixa 側に持たない。向こうが変えてもこちらは追従する。

**比べる相手は `result.output.width/height`**——サーバが ffprobe で測った、返したファイルそのものの
大きさ。`native: true` なら切り抜き後の値（1344×756）になる。

**`result.details.generation.width/height` と比べてはいけない。** こちらは**切り抜く前**の
生成サイズ（1344×768）なので、ファイル（1344×756）と必ず食い違う。
当初この欄を指していたが、vpipe-api から両者の違いを明示されて誤りと分かった
（**契約の字面と目的が食い違った例**。欲しかったのは「生成サイズ」ではなく
「返されたファイルの大きさ」だった）。

どちらも Take の記録に残っている（`raw.output` と `raw.generation`。
`packages/providers/video/src/local-server/provider.ts`）。記録としては両方持ったままでよい。

### 3. technical レビューの解像度検査は「そのモデルが出せる大きさ」と比べる

Project の解像度ではなく、2 の申告値（`raw.output.width/height`）と比べる。
申告が無い素材（持ち込み）は従来どおり Project の解像度と比べる。

fail にするのは次の 2 つだけにする。

- **比がずれている**（Project の比と違う）。枠を埋められないので実害がある
- **申告と実物が食い違う**（`raw.output` と probe が違う）。取り込みの事故

**Project の解像度より小さいこと自体は fail にしない。** 書き出しで拡大するので実害が無い。

**これを直さずに 1 を入れると、全 Take が fail して LLM のレビュー層が丸ごと止まる。**

### 4. 拡大は書き出しの直前に ffmpeg でやる（Chrome にやらせない）

書き出しは Remotion（headless Chrome）で、`<OffthreadVideo style={{objectFit:'contain'}}>` が
コマを `<img>` に描く。**つまりネイティブのまま渡すと、拡大が ffmpeg の Lanczos から
Chrome の拡大に移る。**

実機の Chrome で測った（1344×756 を 1920×1080 に描いて撮影）。

| 拡大 | 輪郭の量 | Lanczos との SSIM |
|---|---|---|
| ffmpeg Lanczos（いま） | 3.049 | — |
| **Chrome** | **2.648（−13%）** | 0.993 |
| ffmpeg bilinear（参考） | 2.607 | 0.995 |

Chrome の拡大は bilinear 相当だった。**画質のための変更で画質を落とすことになるので、
拡大は ixa の手に戻す。**

書き出しの直前に、素材を Project の解像度へ Lanczos で拡大した一時ファイルを作り、
Remotion にはそちらを渡す。保管庫にはネイティブのまま置く。

**probe の大きさが Project の解像度と同じ素材は触らない。** いまの 436 Take は全部素通りするので、
既存と新しい Take が混ざっている期間がそのまま安全になり、無駄な再符号化も起きない。

### 5. 中間ファイルは CRF 16。可逆にしない

「可逆と CRF のどちらにするか」は、**最終出力で見分けられるか**で決めた。

中間ファイル自体を可逆と比べると、素直に単調に下がる（手法の検算）。

| 中間 | SSIM | PSNR |
|---|---|---|
| CRF 12 | 0.992 | 46.7 dB |
| CRF 16 | 0.988 | 44.3 dB |
| CRF 18 | 0.986 | 43.1 dB |
| CRF 20 | 0.982 | 41.8 dB |

ところが書き出し（CRF 18）を通したあとは順位が消える。

| 中間 | 最終出力の SSIM | PSNR |
|---|---|---|
| CRF 12 | 0.985 | 42.5 dB |
| CRF 16 | 0.982 | 41.6 dB |
| CRF 18 | **0.987** | 43.3 dB |
| CRF 20 | 0.980 | 40.9 dB |

CRF 12 より CRF 18 のほうが良い数字になっている。これは順位ではなく揺らぎで、
**書き出し自身の損失が中間の差を飲み込んでいる**ことを示す。中間を良くしても最終出力に届かない。

CRF 16 を採る。元の素材が vpipe 側ですでに CRF 16 なので、新しい粗い量子化を足さずに済む。

一時ディスクのピーク（本制作 116 秒ぶん・1920×1080）:

| 中間 | ピーク |
|---|---|
| 可逆（-qp 0） | 約 2.5 GB |
| CRF 12 | 約 425 MB |
| **CRF 16** | **約 270 MB** |
| CRF 18 | 約 210 MB |

### 6. 切り替えは本制作の仕上げが終わってから

既存の 436 Take は 1920×1080 のまま残るので、作品の中で大きさが混ざる。
4 の判定でそれ自体は安全だが、書き出しの経路が変わる変更を MV の仕上げ中には入れない。

### 7. 対応しているかは `params_schema` を見て判断する

vpipe-api に **2026-10-09 に反映済み**（向こうの main `d23a58d`。制作者の了承済み）。
`/v1/health` の version は 0.1.2 のままなので、**版の番号では判定できない**。

`GET /v1/workflows` の `minimax-h3-turbo-video` に `params_schema.properties.native` が
あるかどうかで見る。**解像度を上げる口（ADR-0044）がワークフローの一覧を引いて
対応を判定しているのと同じ作法**で、モデル ID も版の番号も書き写さない。

`native` を省略したときの Idempotency-Key は反映の前後で変わらない（向こうが揃えてある）。
切り替え前に投げたジョブの再送がすり抜けることはない。

## Consequences

- **プレビューは Chrome の拡大のままで、いまより少し眠くなる。** 比べる Take どうしは
  同じ条件なので採用の判断は狂わない。揃えるなら別の段（作業用を Lanczos で作る）になるが、
  それをやると容量削減が消える
- **一時ディスクを約 270 MB 使う。** 書き出しごとに作って捨てる。保管庫には置かない
- **書き出しの仕様書から署名付き URL が消える。** いまは `apps/api/src/routes/timeline.ts` が
  発行した署名付き URL が `render_jobs.timeline_snapshot` にそのまま保存されていて
  （実際に 17 行）、有効期限 1 時間（`TIMELINE_SIGNED_URL_EXPIRES_SEC`）を過ぎると黙って落ちる。
  **CLAUDE.md 規約 7 違反。** 段 4 で素材をローカルに落とすので、仕様書は素材 ID を持てばよくなる。
  これは段 4 と切り離して先に直してもよい
- **wan-api にも同じ選択肢が要るかもしれない。** 共通層（`local-server`）の作り次第。
  いま決めない
- **容量の削減は向こうの計測でも裏が取れた。** 同じ中身で約 45% 減（合成の試験映像で
  1344×756 が 1.20 MB、1920×1080 が 2.20 MB）。こちらが本制作の素材で測った 40% と整合する

## Alternatives

- **作品全体をネイティブ相当の大きさで組んでから、最後に 1 回拡大する**: 一時ファイルが
  1 本で済む。却下——テロップが小さい大きさで描かれてから拡大されるので、文字が眠くなる。
  テロップは必ず 1920×1080 で描く
- **中間を可逆にする**: 一時ディスクが 2.5 GB になる。上の実測のとおり最終出力に差が出ない
- **`output` を省略可にしてネイティブ全体（1344×768）を返してもらう**: 比率を決める手がかりが
  無くなり、cover の切り抜き規則を ixa が再現することになる。1 の理由で却下
- **Chrome 側で拡大の質を上げる**: CSS の `image-rendering` に Lanczos 相当は無い
