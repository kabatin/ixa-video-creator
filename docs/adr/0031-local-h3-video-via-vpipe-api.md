# ADR-0031: 手元の MiniMax H3 を vpipe-api 経由の Provider として使う

Status: Accepted
Date: 2026-09-30
Decider: Claude（Architect）。制作者の選択（2026-09-30「MV制作ツールからAPIで動画生成を利用できるようにしたい」）

## Context

動画生成の実 Provider は fal.ai（ADR-0013）だけで、1 生成ごとに費用が掛かる。
制作者は手元の Mac（M5・10 コア GPU・32GB）で MiniMax H3（FL2VA・8bit）+ Turbo LoRA を動かしており、
それを HTTP で包んだ別リポジトリ **vpipe-api**（https://github.com/kabatin/vpipe-api）を作った。
契約の正は vpipe-api の `docs/api.md`（投入 202 → 状態の問い合わせ → 出力の取得。満杯は 429）。

実測（M5・32GB）で分かっていること:

| 生成 | 所要時間 |
|---|---|
| draft 832x480 × 124 コマ | 約 7 分 |
| standard 1024x576 × 124 コマ | 約 10.6 分 |
| standard 1024x576 × 243 コマ | 約 24 分 |

- 作れるのは **17n+5 コマ（n = 3..14、56〜243 コマ）・24fps** だけ。出来たコマ数はそのまま返り、切り詰めない
- GPU の枠は 1 つ。走っている 1 本と待ちの 1 本で埋まり、それ以上は **429 `busy`**（`Retry-After` 付き）で断る
- 出力は H.264・24fps・**音声トラック無し**。サーバが小さく作って、頼んだ大きさへ拡大する（cover + 中央切り抜き）
- サーバは既定で `127.0.0.1` に待ち受ける。ループバック以外で待ち受けるならトークン必須で、無ければ起動しない

## Decision

### 1. Provider `vpipe` とモデル 2 つ（AUTO には選ばせない）

`packages/providers/video/src/vpipe/` にアダプタを足す（fal と同じく素の `fetch`。`fetch` は注入）。

| モデル | 段 | 所要時間の見込み |
|---|---|---|
| `vpipe/minimax-h3-turbo-draft`（MiniMax H3 Turbo 下書き（ローカル・無料）） | draft | 420 秒 |
| `vpipe/minimax-h3-turbo`（MiniMax H3 Turbo（ローカル・無料）） | standard | 640 秒 |

- **`routable: false`。** 1 本に 7〜25 分かかり 1 本ずつしか作れない。しかも費用 0 は Router のスコアで
  圧倒的に有利なので、候補に入れると AUTO が黙ってこちらへ寄る。生成欄で明示して選んだときだけ動く
- 費用は 0（手元の GPU）。**スタブ扱いにしない**（`STUB_PROVIDER_IDS` に入れない。ADR-0025 の `local` と同じ）
- qualities は**未実測の相対値**（サンプル 40 本を目で見た印象）。所要時間と能力は実測

### 2. 尺は H3 が素で出せる長さだけを宣言する（切り詰めない）

`durations: { mode: 'enum', values: [2.333, 3.042, 3.75, …, 10.125] }`（17n+5 コマ ÷ 24、小数 3 桁）。

範囲で宣言すると、4 秒の要求に 4.458 秒の映像が返り、切り詰めが要る。最後のフレームを条件にした生成では、
切り詰めはその最後の絵を捨てることになる。素の長さを宣言すれば ADR-0011 の切り上げがそのまま載り、
`round(秒 × 24)` で 17n+5 のコマ数へ戻せる（戻せなければ投げる。黙って近いコマ数へ丸めない）。
生成尺と実測尺の差は 0.001 秒未満で、technical レビューの尺の検査（±0.05 秒）も通る。

### 3. 解像度は Project の値そのもの（拡大はサーバ）

16:9 / 9:16 / 1:1 / 4:5 の 1080 級と 720 級、計 8 通り（1920x1080・1280x720・1080x1920・720x1280・
1080x1080・720x720・1080x1350・864x1080）を宣言する。サーバがちょうどその大きさへ拡大するので、
technical レビューの解像度の検査も通る。24fps だけ。negative prompt は宣言しない（ガイダンス蒸留済みで効かない）。

### 4. 参照は「開始画像」1 枚だけ

`start_frame` と `previous_shot_last_frame` を受け、どちらも vpipe-api の `start_image` へ写す（ADR-0016）。
両方あれば `start_frame` を使う。枠は 1 つなので残りは使わないが、**黙って捨てず Take の記録（raw）に残す**。
`poll` には仕様が渡ってこないので、投入時に出力の置き場へ控え（素材 ID と role だけ。URL と画像の中身は入れない）を書き、
完了時に読む。控えが読めなければ推測で埋めず null にする。選び方は仕様の純関数なので `Take.spec` から再現もできる。

画像は署名付き URL から取り寄せて base64 で送る（サーバからストレージが見えるとは限らない）。PNG・JPEG・WebP・20MB まで。
`Content-Length` を先に見て、読みながらも 20MB を超えた時点で止める（丸ごと読んでから確かめない）。
`end_frame`（最後のフレーム）は vpipe-api が受けるが、ixa にまだ付ける画面が無いので宣言しない。**次の段階**で足す。

### 5. 満杯は失敗にしない（`ProviderBusyError`・冪等キー・12 時間の期限）

**Architect の変更（`packages/providers/core` と worker）。**

- `ProviderBusyError`（`ProviderError` の一種・常に retryable・`retryAfterMs` を運ぶ）を core に足す。
  意味は「後で**同じ投入を**やり直して」。vpipe アダプタは次のときにこれを投げる
  - 投入が 429 で断られた（何も積まれていない。`Retry-After` を運ぶ）
  - 投入の前の空きの確認（`GET /v1/health`）で `running + waiting >= 1 + max_waiting` だった
    （待ちの目安 120 秒）。満杯のまま投入を繰り返すと、そのたびに署名付き URL を作り直し、最大 20MB の画像を読んで
    base64（約 27MB）で送り、429 で捨てられる。確認は節約のためでしかなく、本当の門番は投入の 429
    （確認の応答が読めなければ確かめずに進む。接続を拒まれたら＝サーバが止まっているならそのまま失敗にする）
  - 冪等キー付きの投入を送ったのに応答が失われた（時間切れ・切断・本文の途中で切れた）、またはサーバが
    やり直せると言う失敗（5xx）だった。受け付けられたかは分からないが、同じキーで投げ直せば同じジョブが返る
- **冪等キー**: `VideoGenerationRequest` に任意の `idempotencyKey` を足す（後方互換。対応しない Provider は無視する）。
  worker は GenerationJob の ID を渡し、vpipe アダプタは `Idempotency-Key` ヘッダで送る。vpipe-api は同じキー・
  同じ中身の投入に、新しく作らず既存のジョブを `200` で返す（429 にもしない）。同じキーの投入がまだ処理中なら
  `409 idempotency_in_flight`（retryable。`ProviderBusyError` にして後で投げ直す。時間切れのすぐ後の投げ直しで起きうる）。
  同じキーで中身が違うなら `409 idempotency_conflict`（やり直せない失敗として終端にする。仕様は spec_drift の検査で
  固定しているので、中身が違うのは配線の誤りしかない）。
  **キーの無い投入では、応答が失われても `ProviderBusyError` にしない**（投げ直すと二重に生成しうる）
- 接続を拒まれた（`ECONNREFUSED` など。要求は届いていない）ときは、キーがあっても「サーバが起動しているか確かめて」の
  失敗にする。サーバが止まっているのに 12 時間黙って待たせない
- worker の投入の口（`processor.ts`）は、`ProviderBusyError` を受けたら**ジョブを失敗にせず queued のまま**、
  `Retry-After` を 30 秒〜10 分に収めた待ち（既定 60 秒）で同じジョブを予約し直す。`running` にしない・
  出来事を流さない・**`attempt` を増やさない**。次の回も系譜と仕様の検査（spec_drift）から通る。
  上限を 10 分まで取るのは、走っている 1 本が 7〜25 分かかり、サーバが長めに待てと言うならそれに従うため
- 予約し直せなければ（キューに入れられない）、queued のまま取り残さず終端の失敗にする（何も投入していない）
- 積んでから **12 時間**（`SUBMIT_BUSY_DEADLINE_MS`、`queuedAt` から数える）を過ぎたら
  `provider_busy_timeout` で終端にする（やり直せる失敗として記録する）

`attempt` を使わない理由: ポーリングの上限（vpipe は 30 秒おき・360 回で約 3 時間。§5b）は**投入後**の待ちのためのもので、
順番待ちに食わせると、長い列の後ろほど走る前に尽きる。一方、受け付けられたジョブの前には（vpipe-api の待ちの枠が
既定の 1 なら）走っている 1 本しかいないので、最悪でも約 48 分（24 分 × 2）で終わり、上限に収まる。12 時間は、1 本 7〜25 分で 1 本ずつなら
30 本前後の列を捌ける長さで、それでも空かないのはサーバが詰まっているとみなす（黙って永遠に待たせない）。

断られたジョブは空いた順ではなく予約の順に投入し直され、並びは FIFO にならない。**頼んだ順に仕上がるとは限らず、
理屈の上では 1 本が期限（12 時間）まで取り残されうる**（空いた瞬間に毎回ほかのジョブが先に投入する場合）。

**待っている間の spec_drift**: 連続性の参照（前の Shot の最後のコマ）は前の Shot の**採用 Take** から決まる
（`packages/generation/src/context.ts` の `previousShotLastFrame`）。待っている間に前の Shot で採用し直すと、
この Shot の仕様が変わって spec_drift で止まる。仕様が本当に変わったので止めるのが正しい（古い最初のフレームで作らない）。
待ちが長い Provider では起きやすいので、画面に出る文でその理由（前の Shot の採用 Take が変わった）を言うようにした
（内部のハッシュは文に入れずログに残す）。

冪等キーで投げ直した投入が、確認で満杯と言われ続けることはある（待ちの枠にいるのが自分のジョブのとき）。
そのジョブが走り出して枠が空けば、同じキーの投入が既存のジョブを返すので、遅れは最大でも 1 本分で済む。

### 5b. 問い合わせは 30 秒おき（Provider ごとの問い合わせの方針）

**Architect の変更（`packages/providers/core` と worker）。** 制作者の判断（2026-09-30「30 秒ごとに問い合わせる」）。

実機の E2E では、worker の既定（5 秒から倍々に伸ばして最大 2 分おき・60 回）のせいで、サーバが作り終えてから
ixa が気付くまで **9〜99 秒**遅れた。1 本 3〜25 分の生成に最大 2 分の遅れは大きい。問い合わせ先は手元のサーバなので、
細かく聞いても費用も負荷もほとんど無い。

- `VideoProvider` に任意の `pollPolicy: { maxIntervalMs, maxAttempts }` を足す（後方互換。省略は既定のまま）
- worker（`apps/worker/src/generation/poll-policy.ts`）は、伸ばし方（5・10・20 秒…）はそのままに、
  間隔の上限と諦める回数だけ Provider の方針を使う。問い合わせが一時的に失敗したときの予約し直しも同じ方針に従う
- vpipe は **30 秒おき・360 回**（冒頭を含めて約 179 分）。回数は投入後の最悪の待ちを覆うように取る:
  前の 1 本（243 コマの standard で約 25 分）+ 自分（約 25 分）= 約 50 分に、サーバの再起動や
  書き出し・Codex とのメモリの取り合いで遅くなる分を見て約 3 時間
- fal・スタブ・ローカルの画像→動画は方針を持たず、今までどおり

### 6. 出力は手元のファイルで返す（SSRF 検査を緩めない）

出力 URL は `127.0.0.1` を指すので、`{ type: 'remote' }` で返すと worker の SSRF 検査に正しく止められる。
検査は緩めず、アダプタが自分で取り寄せて `{ type: 'local', path }` で返す（`ProviderOutput` を型で分けている理由）。

- `<outputDir>/.tmp/<ジョブ ID>.<乱数>.part` へ流しながら書き、書き終えてから `<outputDir>/<ジョブ ID>.mp4` へ rename する。
  既にあれば取り寄せない（同じジョブを 2 度問い合わせても 1 本）。途中で切れたら読み取りを取り消し、書きかけを消して、
  やり直せる失敗として投げる。1 本 2GB を超えたら止める（壊れたサーバにディスクを埋めさせない）
- 状態応答のジョブ ID が問い合わせたものと違えば、取り込まずにやり直せない失敗にする（出力のファイル名もジョブ ID で決まる）
- 投入のたびに、24 時間より古い自分のファイル（mp4・書きかけ・控え）を消す。掃除は投げない
- `outputDir` は worker が `<STUB_OUTPUT_DIR>/vpipe`。ジョブ ID はファイル名と URL に使うので、使える文字を絞って検証する

問い合わせの HTTP の失敗は `failed` を返さず**投げる**。retryable なら worker が捨てずに予約し直す
（サーバの再起動中に 1 回つながらなかっただけで、走っている生成を捨てない）。**本文が途中で切れた・時間切れも
通信の失敗として投げる**（応答の形の違い＝終端の失敗と取り違えない）。通信の失敗は 2 つに分ける:
`vpipe_unreachable`（接続拒否など。要求は届いていない）と `vpipe_no_response`（届いたかもしれない）。
サーバの文は、URL と絶対パス（`/Users/<名前>/…` など）を落としてから理由として運ぶ。
ジョブ自体の失敗（`failed`）はサーバの `retryable` のまま、`canceled` はやり直せない失敗として返す。

### 7. 設定は明示の切り替え

- `LOCAL_VIDEO_GENERATOR=none|vpipe`（既定 `none`）。**URL やトークンの有無で切り替えない**（LESSONS「鍵があることを、実行の合図にしない」）
- `VPIPE_API_URL`（既定 `http://127.0.0.1:8765`）、`VPIPE_API_TOKEN`（空なら未設定。Bearer で送る）
- `vpipe` でこのマシンの外を指しているのにトークンが無ければ、**起動時に止める**（その設定は必ず 401 になる）
- API と worker の両方で、`vpipe` のときだけ登録する（API はモデル一覧・見積り・検証のため。作るだけでは通信しない）
- 設定 →「接続先と実行の設定」に切り替えと合言葉の有無を出す（URL と値は出さない）。
  別のマシンのサーバを http で使う設定なら、合言葉と画像が暗号化されずに流れること（信頼できる LAN だけで使う）も書く

## Consequences

- 生成欄のモデル選択に「MiniMax H3 Turbo（ローカル・無料）」が 2 つ出る。1 本 7〜25 分。まとめて頼むと 1 本ずつ順に仕上がる
- **32GB の機械では、生成中に書き出し（Remotion）や Codex CLI を同時に回すとメモリを取り合う。**
  H3 の 8bit でも生成中はメモリの大半を使うので、スワップで全部が遅くなる。重い作業は生成の合間に回す
- 出力に音は無い。ixa は楽曲を別に持ってタイムラインで音を組むので困らない（fal でも音は切っている）
- サーバの再起動で走っていたジョブは `server_restarted` で失敗する（やり直せる失敗として記録）。自動では投げ直さない
- 生成中に `LOCAL_VIDEO_GENERATOR` を `none` に戻すと、そのジョブは未登録のモデルとして失敗する（fal と同じ）
- **ライセンス**: モデルの重みは MiniMax H3 Community License で、利用できる地域・用途に制限がある。
  ixa は重みを同梱せず vpipe-api も別リポジトリだが、有効にする人はその条件に従う必要がある（README の第三者ライセンスに記載）

## やらないこと（今回）

- 最後のフレーム（`end_frame`）を付ける画面と、それを `end_image` へ写すこと（次の段階）
- 進み具合（`progress`）の画面表示。値は Provider の状態には載せている
- `server_restarted` のときの自動の投げ直し
- 断られたジョブを頼んだ順に並べ直すこと（FIFO の保証）

## 追記（2026-10-02）: PR #4 レビューの指摘を直す

- **サーバのエラー（5xx）は満杯ではない。** 冪等キーがあればその場で 3 回まで投げ直し、続けばサーバの理由で失敗にする。
  以前は満杯と同じ待ち行列に回り、60 秒ごとに開始画像を送り直しながら最大 12 時間回って「順番が回ってこなかった」と言っていた。
  満杯として待つのは 429・health の満杯・同じキーの投入が処理中（409 idempotency_in_flight）・応答なし だけ
- 待つときは断った理由をログに残す（warn）
- 接続の時間切れ（`UND_ERR_CONNECT_TIMEOUT`）は「届いていない」。別の Mac が眠っているときに 12 時間待たず、すぐ失敗にする
- 投入前の空きの確認は 5 秒で切る（答えない vpipe で、同じキューの fal やスタブの生成を分単位で待たせない）
- 失敗で終えたジョブ（問い合わせの上限など）は、生成先にも止めてと頼む（GPU を占め続けない）。生成をやめる と同じ口。
  応答が失われた投入のあとで諦めたときは、生成先の ID が分からず止められない（vpipe-api に冪等キーで引く口が無い）
- 掃除・投入の控えの失敗はログに残す（生成は止めない）。合言葉が開始画像（署名付き URL）の取得に載らないことをテストで押さえた
