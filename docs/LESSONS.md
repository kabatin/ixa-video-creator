# 実装で踏んだこと

このプロジェクトで実際に起きた失敗と、そこから決めた規則。
一般化できるものだけを残してある（内部の作業記録そのものはリポジトリに入れていない）。

共通しているのは **「テストが緑でも、何も確かめていないことがある」** という形。
以下はほぼ全部その変種である。

---

## 1. 検査が素通りする形

### スキップして空を返すと、下流で「合格」に化ける

レビューの一段目は、判定できるフレームが 1 枚も無いときレビュアを呼ばずに空配列を返していた。
呼ばない判断自体は正しい。画像なしの依頼はスキーマ検証で落ちるし、見ずに出した判定を
残すべきでもない。

**しかし空配列は集約で pass になった。** 集約は「fail があれば fail / warn があれば warn /
どちらも無ければ pass」なので、指摘ゼロは合格である。結果、**7 レビュアのうち 4 つが一度も
動いていない Take が「レビュー済み・合格」として画面に出た。**

ユニットテストは通っていた。テスト自身が `findings: []` という誤った期待を固定していたため。

> 集約関数は「問題が無かった」と「そもそも見ていない」を区別できない。
> スキップの分岐で空を返すと、その区別が静かに消える。消えた先が合格なら、人は検査されたと信じる。

**規則**: スキップして空を返す分岐を書いたら、その値が最終的にどう畳まれるかを 1 段ずつ辿る。
畳んだ先が「異常なし」になるなら、**飛ばした事実を値として残す**。どの検査が飛んだかまで残す。

### 制約を足したら、それを破る値のテストも置く

zod に制約を足したとき、「制約を外しても 1 件も落ちない」テストを 4 回書いた。
通る値ばかりを入れていたので、検査が存在しなくても緑のままだった。

**規則**: 制約を足したら、**それを破る値を 1 つ入れる**。制約を外して落ちることを確かめる。

### 片方の経路だけで試すと、もう片方は素通りする

ローカルの GPU を 1 本ずつに揃える仕組み（ADR-0040）に、「1 本目が終われば 2 本目が投入される」
というテストを書いた。1 本目は**失敗で**終わらせていた。

**実装から「終わったら順番を返す」を消しても、そのテストは通った。** 失敗の経路には終端の処理に
もう 1 つ返す口があり、そちらが代わりに返していたため。成功で終わる経路は誰も試していなかったので、
「成功したら順番を押さえたまま」になっていても緑のままだった。

終端が 2 つ以上あるもの（成功 / 失敗 / 取り消し）では、**片方だけ試したテストは、
もう片方の経路について何も言っていない。**

**規則**: 後始末（資源を返す・状態を戻す）を書いたら、**終端ごとに**試す。
そして実装からその後始末を消して、**どのテストが落ちるか**を見る。1 つも落ちないなら、
落ちるテストを足すまで終わっていない。

### 件数だけを見る要約は、分類が欠けても気づかない

「27 件中 16 件」のような要約だけを検査していると、分類のうち 1 つが丸ごと抜けても
合計が合っていれば通る。

**規則**: 要約を検査するなら、**分類ごとの内訳**も見る。

### 安全網は、自分で壊して確かめる

境界ルール・漏洩検査・網羅テストを書いたら、**実装をわざと壊して、そのテストが落ちることを
確認する**。このプロジェクトでは、壊しても落ちない検査が何度も見つかった。典型は
「定数どうしを比べていて何も確かめていない」形（`expect(cost).toBe(4 * RATE)` のように、
実装と同じ定数を使う）。

**規則**: 期待値には**実数**を書く。壊して確かめるときは、先にファイルを退避する
（`git checkout` は HEAD へ戻すので、未コミットの実装ごと消える）。
**退避先ではファイル名が衝突する。** 別のフォルダにある同名のファイル（`asset-folder.ts` が
2 つ）を 1 つの退避先へまとめてコピーし、片方が上書きされたまま「戻した」ことがある。
退避はフォルダの形ごと取るか、名前を分ける。

### 外しても緑なら、その安全網の目的を取り違えている

「もう入っていれば触らない」という検査を外しても、テストは全部通った。
あとから同じ結果になる経路（`EEXIST`）があったからで、**その検査は重複ではなく、
別の目的を持っていた**（もう入っているものについては元の素材を見に行かない。
見に行くと、利用者が消した素材を毎回「見つかりません」と言い続ける）。

**規則**: 外しても落ちない検査を見つけたら、消す前に「何のために置いたのか」を言葉にする。
言葉にできたら、**その目的を確かめるテストを足す**。言葉にできないなら消す。

## 2. 「無い」と「読めなかった」を混ぜない

生成結果・解析・一覧などで、**読めなかったときに空を返す**と、利用者には「0 件」に見える。
この 2 つは意味が正反対で、前者は待てば直り、後者は操作しないと直らない。

実際に起きたもの:

- 履歴の取得に失敗 → 空配列 → メニューが「戻せる操作がありません」と表示。
  通信不良が「もう戻せない」に化けた。
- モニターが `document === null` を「Shot が 0 件」と同じ扱いにしていた。
  どちらも黒画面だが、意味が違う。

**規則**: `null`（まだ読めていない）・失敗（読めなかった。理由を持つ）・空（読めた結果 0 件）を
**別の状態として持つ**。型で分ける。画面の文面も分ける。

---

## 3. 規則を 2 箇所に書くと、必ずズレる

`formatDuration` という同名の関数が 2 つのモジュールにあり、**宣言している規則が正反対**だった。

- 片方: 「尺は秒（`3.75s`）。時計形式だと長さに見えない」
- もう片方: 「尺は時計形式と生の秒を併記する（`0:03.75（3.75s）`）」

どちらを import したかで同じ値が別物に見え、画面ごとに表記が割れていた。しかも前者のファイルの
冒頭には「秒の表示を 1 箇所に集める。以前は 4 通りが混在した」と書いてあった。
**一度直した二重化が、隣で復活していた。**

同じ型の事故は他にもあった。識別画像のラベルが 2 箇所にあり、`face_side` が
「顔（横）」と「顔（側面）」でズレていた。

3 つ目は**表示ではなく判定**がズレていた。「Take が尺に足りているか」の規則が
再生側（`@ixa/timeline`）と自動レビュー（`@ixa/review`）の 2 箇所にあり、レビューだけが
`Shot.timing`（ゆっくり再生で埋める設定）を見ずに引き算していた。**埋まっている Shot が必ず
`fail` になる**状態で、最長の短い生成 AI を選んだ瞬間に全 Shot で出る。
直し方は「レビュー側にも同じ条件を足す」ではなく、**純粋な規則を共通の依存（domain）へ移して
両方が同じ関数を読む**こと。条件を足すだけでは、次に幅が変わったときまたズレる。

**規則**: 正を import できないなら、規則を書き写さず**取りに行く口**を作る。
書き写すしかないときは、**2 つが同じものを指していることを検査で固定する**。
依存の向きで import できないなら、**規則を共通の依存（domain）まで下ろす**。

## 4. 実機でしか出ないもの

### ブラウザで触るまで UI は検証されていない

ユニットテストが全部緑でも、実際に開くと「押して何も起きない」「見切れる」「そもそも到達できない」
が出る。実例:

- パネル一覧から 1 枚が漏れていて、狭い画面では**その機能に到達する手段が 3 つとも無反応**だった。
  テストはパネル定義しか見ていなかったので素通りした。
- パネルを改名したのに、保存済みのレイアウトが**古いタブ名を持っていた**（`toJSON()` が
  タイトルも保存する）。テストは定義を見ていたので緑。

**規則**: 画面に関わる変更は、**実機で見るまで完了としない**。網羅は集合として検査する
（「一覧 A の全要素が一覧 B にある」）。

### 置き場を替えたら、外向きの設定が 1 つ残っていないか見る

素材を MinIO から手元のファイルへ移したあと、**手元のブラウザでは全部見えるのに、LAN の別の
端末では絵も動画も 1 つも出なかった**。API は `macbookpro.local:3001` で呼ばれているのに、
素材の URL だけ `127.0.0.1:3001` を返していたため（その端末自身を指す）。

MinIO のときは `S3_ENDPOINT` に LAN の名前が書いてあった。接続先の設定を丸ごと置き換えたので、
**そこに入っていた「外から届く場所」という情報だけが落ちた**。移行の検証は同じ機械で行ったので、
最後まで気づかなかった。

**規則**: 「どこから届くか」を持つ設定を置き換えるときは、旧設定の値を 1 つずつ読み、
同じ意味の行き先が新しい側にもあるかを確かめる。既定は**別々に持たず、既にある 1 つを読む**
（素材の URL の宛先は `NEXT_PUBLIC_API_URL` を既定にした）。手元で動いたことは、
別の端末で動くことの証明にならない。

### 手元のコマンドが CI と同じ形か確かめる

同じ日に 2 回踏んだ。

- **vitest は型を見ない。** テストを足して vitest が緑・lint も緑でも、`tsc` を回していなければ
  型エラーはそのまま入る。実際に branded 型の誤用が main に入った。
- **リポジトリ直下からの `eslint <path>` は型情報が付かない。** 型を要するルールが
  そもそも効かず、CI（各パッケージの `eslint src`）でだけ落ちた。

**規則**: push 前に **CI と同じ形**で lint / typecheck / test を回す。順番は tsc → vitest → eslint。
モノレポなら並列度を絞って全体を回す。

### 負荷を見てから並列度を上げる

全体テストを複数の並列作業から同時に走らせて、開発機が止まった。ワーカー数を絞る指定が
逆に起動時に落ちる、という罠もあった。

**規則**: 検証は**範囲と並列度を絞る**。全体を回すときは並列度を明示する。

## 5. 実データは想定と違う

### 論理削除された行を数えてしまう

「Shot が 68 件ある」と思って計測していたが、生きているのは 27 件だった。残りは論理削除済み。
リポジトリ層は除外していたが、直接数えた箇所が除外していなかった。

### 「出ないはずのものが出ない」ときは、まずデータを疑う

機能が動いていないのか、そもそも該当データが無いのかを先に分ける。

### 分布を見ると、思い込みが崩れる

「拍からズレている 16 件」を警告として赤で出していた。実際に分布を測ると、ズレは
**半拍の 56〜91% に集中し、0〜0.136 秒には 1 件も無かった**。手で外したならそこに散らばる。
つまりそれは拍ではないもの（歌い出し・言葉の頭）に合わせて切った**編集の意図**であって、
間違いではなかった。

**規則**: 道具が編集の意図を間違いと決めない。数えて並べるところまでが道具の仕事。
警告を出す前に、**それが本当に異常かを分布で確かめる**。

## 6. お金が動くところ

### 無料のうちに、課金経路を通しで走らせる

実 Provider を繋ぐ前、このプロジェクトには 2 つの「初回が本番」があった。

- **生成が失敗したときの経路が一度も走っていなかった。** ローカルのスタブに失敗を起こす口が
  無かったため。しかも失敗時に Shot を解放する処理が抜けており、失敗した Shot は DB ごと
  「生成中」で固まって二度と生成できなくなる状態だった。
- **予算ガードが構造上発火しなかった。** スタブの単価が 0 で、見積が常に 0 になるため。
  ドメインの単体テストは緑だったが、API から 422 が返るところは誰も確かめていなかった。
  実際に予算 $0.01 で一括生成を投げたら、6 件すべて通った。

どちらもスタブに**失敗注入と架空の単価**を足して、1 円も使わずに経路を走らせられるようにした。

### 課金済みの仕事を、こちらの都合で捨てない

問い合わせ中に一時的な 5xx が返ると、`retryable` を見ずに終端の失敗として扱い、
**Provider 側で走っている（＝課金が確定している）生成を捨てていた**。

**規則**: 投入済みかどうかで扱いを変える。投入前の失敗は捨ててよい（まだ払っていない）。
投入後は、やり直せる失敗なら予約し直す。

### 鍵があることを、実行の合図にしない

「鍵が設定されていたら実 Provider を使う」は事故のもと。別の理由で鍵を置いた瞬間に
課金経路が開く。**金が動く切り替えは明示にする**（このプロジェクトでは `VIDEO_PROVIDER`）。
そして、選んだのに鍵が無ければ**黙って無料の方へ落とさず、起動時に止める**。
落とすと「実 Provider で作ったつもりの偽物」が成果物として残る。

### 出せない数字は、出せないと書く

事前見積の API が無いのに金額欄を空のままにすると、「取り消せません・費用が発生します」と
警告しながら金額だけ伏せることになる。**空欄にせず「いまは出せない」と書く**。

推測で単価を埋めるのも同じ理由で危ない。安すぎる数字を置くと予算ガードが素通りし、
気づくのは請求が来てからになる。**出どころの分かる値を残して「未確認」と明示する。**

## 7. 画面に出す言葉

- **URL とレスポンス本文を利用者に出さない。** 例外の `message` をそのまま表示していたため、
  完全な URL とレスポンス 500 文字が画面に出ていた。呼び出し元は 46 ファイルあったので、
  **出口を 1 つにして**直した。
- **実装の名前を出さない。**「worker のログを確認してください」は、映像を作りに来た人に
  実行できない指示である。
- **署名付き URL はログにも例外にも載せない。** DB に保存しないだけでは足りない。
- **同じ語を 2 つの意味で使わない。** 「素材」がワークスペース全体・1 件を見るパネル・
  Take の動画ファイル の 3 つを指していた。

## 8. 契約と目的が食い違ったら、黙って従わない

インターフェースの字面どおりに実装すると目的が成立しない、という場面が複数あった。

例: `poll` は仕様を受け取らず、Provider の応答にも尺が無いため、素の識別子だけを持つと
worker 再起動後に費用が 0 に化けて「無料だった」として記録される。
ハンドルの参照は契約上「不透明・形は Provider ごと」なので、そこに尺を載せて解決した。

**規則**: 字面と目的が食い違ったら、勝手にどちらかを選ばず、**形を変えた案と理由を出して相談する**。

## L-036: 早い者勝ちの順番待ちは、列の長いほうが勝ち続ける（2026-10-08）

**何が起きたか**: 2 作品の動画生成を一晩分まとめて積んだら、**後から積んだ作品が全部終わり、
先に積んだ作品は 5 時間 1 本も進まなかった**。手元の GPU は 1 本ずつで、順番待ちのジョブは
「空いていたら貰う、埋まっていたら 60 秒寝てまた来る」だった。整理券が無いので、
GPU が空いた瞬間に起きていた者が勝つ。69 本の列と 16 本の列では、抽選は 69 本のほうが勝ち続ける。

**気づけたか**: コードには「理屈の上では 1 本が期限まで取り残されうる」と書いてあった。
**書いてあることと、起きてよいことは違う。** 確率が偏る条件（列の長さが違う）を足したのは
一括投入の導線を作った自分で、そのとき「取り残されうる」の確率が跳ね上がることを見ていなかった。

**規則**: 共有資源の順番待ちを「空いていたら取る」で書かない。**積んだ順の整理券**にする。
偏りは「起こりうる」ではなく「列が長いほうが必ず勝つ」になる。
実測で確かめるなら、**1 時間ごとの完成数を作品ごとに並べる**（平均では見えない。
5 時間 0 本と 10 本/時が平均では「進んでいる」に見える）。

**併せて**: 整理券にすると、先頭が寝ている間は資源が遊ぶ。**先頭だけ短く起こす**
（後ろは起きても取れないので、叩かせる意味が無い）。
